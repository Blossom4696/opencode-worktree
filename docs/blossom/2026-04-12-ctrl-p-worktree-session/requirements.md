# 需求文档

## 需求概述

### 功能简介
为 `ctrl+p` 命令面板新增一个“隔离工作树会话”能力。用户输入工作树名称，并可选输入自定义目录名；系统按两种模式启动：基于当前会话某条消息 fork 新会话，或直接创建新会话；随后创建新的 git worktree、初始化分支、在新 worktree 中启动 agent，并将提示词发送给该新会话执行。

### 价值主张
- **用户价值**: 用户可以在不污染当前工作区的前提下，快速开启一个带独立分支与独立上下文的新任务会话。
- **业务价值**: 降低多任务并行与实验性开发的操作成本，提升 worktree 工作流在 TUI 内的可用性与闭环程度。
- **解决问题**: 解决“手动命名 worktree、决定目录位置、创建分支、切目录、开新 session、fork 上下文、再发送 prompt”链路过长的问题。

## 功能需求

### 用户故事 1
**作为一名** 在 TUI 中工作的用户，**我希望** 通过 `ctrl+p` 输入工作树名称、可选目录名与提示词来创建隔离 worktree 会话，**以便于** 用最少步骤开启一个不影响当前工作区的新任务。

#### 验收标准
- [ ] **场景 1.1**: 用户从 `ctrl+p` 触发该能力，选择“新 session”模式并输入工作树名称与提示词。
  - **预期结果**: 系统基于用户输入的工作树名称生成分支名，创建新的 worktree 与分支，在新 worktree 中启动新 session，并自动将提示词发送给该 session。
- [ ] **场景 1.2**: worktree 创建成功后，新 session 的工作目录为新 worktree。
  - **预期结果**: agent 后续看到的当前工作区、路径解析与文件操作范围都落在新 worktree 内，而不是原工作区。
- [ ] **场景 1.3**: 用户未输入自定义目录名。
  - **预期结果**: 系统在 git 根目录父目录下创建与当前仓库同级的新目录，目录名默认为“git 根目录文件夹名 + 工作树名称”的规范化拼接结果。
- [ ] **场景 1.4**: 用户输入自定义目录名。
  - **预期结果**: 系统仍在 git 根目录父目录下创建 worktree，但目录名使用用户提供的自定义名称。

### 用户故事 2
**作为一名** 已经在某个会话中积累上下文的用户，**我希望** 从当前会话某条消息 fork 到用户命名的新 worktree 会话，**以便于** 继承已有上下文并在隔离分支内继续任务。

#### 验收标准
- [ ] **场景 2.1**: 用户选择“从消息 fork”模式后，可从当前会话的可 fork 用户消息中选择来源消息。
  - **预期结果**: 新 session 基于所选消息 fork，而不是从空白上下文开始。
- [ ] **场景 2.2**: 用户完成消息选择，并输入工作树名称与提示词后，系统在新 worktree 中打开 fork 后的新 session。
  - **预期结果**: 新 session 保留原链路上下文，并在新 worktree 中继续执行新增提示词。
- [ ] **场景 2.3**: fork 模式未输入自定义目录名。
  - **预期结果**: 默认目录命名规则与“新 session”模式一致，仍位于 git 根目录父目录下。

### 用户故事 3
**作为一名** 需要稳定闭环的用户，**我希望** 系统在异常情况下给出明确结果与恢复路径，**以便于** 我不会因为半成功状态而失去控制。

#### 验收标准
- [ ] **场景 3.1**: worktree、session fork、prompt 发送、打开终端/窗口等任一步骤失败。
  - **预期结果**: 系统明确提示失败发生在哪一步、哪些资源已创建、是否需要手动恢复，以及下一步建议操作。
- [ ] **场景 3.2**: prompt 自动发送失败但 worktree 与新 session 已成功创建。
  - **预期结果**: 系统保留已创建资源，并明确提示用户可手动进入该 session 补发 prompt。

## 非功能需求

### 性能要求
- **响应时间**: `ctrl+p` 触发后的交互反馈应立即可见；进入执行后应尽快返回“创建中/已启动/失败”状态，避免无反馈等待。
- **并发能力**: 应支持同一仓库存在多个 worktree 会话，不要求串行独占。
- **资源消耗**: 不引入新的常驻后台服务；复用现有 worktree、session、terminal 打开链路。

### 安全要求
- **数据保护**: 不得把原会话外的无关上下文注入新 session；仅复制既有允许复用的 session/workspace 数据。
- **访问控制**: 仅允许在当前仓库上下文中创建 worktree；分支名、路径与命令参数需继续沿用现有校验策略。
- **合规性**: 不新增超出现有终端打开、git worktree、session fork 机制之外的权限要求。

### 可靠性要求
- **可用性**: 任一步骤失败都不能让用户处于“是否成功未知”的状态。
- **容错性**: 对部分成功场景要给出保留资源还是回滚资源的明确策略；默认优先保留已成功创建的 worktree/session，并提示手动恢复方式。
- **数据一致性**: worktree 路径、目录名、分支记录、session 绑定关系需要与实际创建结果一致，避免 UI 与真实状态不一致。

### 可用性要求
- **易用性**: 入口位于 `ctrl+p`，单次流程内完成模式选择、工作树名称输入、可选目录名输入、提示词输入与启动，不要求用户先切换到终端手工补步骤。
- **可访问性**: 继续遵循现有 TUI command/dialog 交互模式。
- **国际化**: 不适用，沿用当前项目中文文案策略。

## 约束条件

### 技术约束
- **技术栈限制**: 复用现有 `tui.tsx` 命令注册、`worktree.ts` 创建链路、`fork-session.ts` fork 链路、`terminal.ts` 启动链路，不新增重型中间层。
- **系统依赖**: 依赖现有 git worktree、OpenCode session fork/prompt API、终端/ tmux 打开能力。

### 业务约束
- **时间限制**: 本期只覆盖 `ctrl+p` 内的一键启动闭环，不扩展到完整 worktree 管理台。
- **预算限制**: 不新增外部服务与付费依赖。

## 依赖关系

### 前置条件
- 当前目录是有效 git 仓库，且现有 worktree 插件链路可用。
- git 根目录父目录可写，用于创建与当前仓库同级的新 worktree 目录。
- 当前环境可创建 worktree，并可启动新 terminal/tmux 窗口。
- 若选择“从消息 fork”模式，当前页面必须处于 session 上下文，且存在可 fork 的用户消息。

### 后续影响
- TUI 命令面板将新增一个面向 worktree 新会话的统一入口。
- worktree/session 状态管理、失败提示与终端拉起链路需要配合该新入口。

## 验收测试标准

### 功能测试
- [ ] 所有用户故事的验收标准通过
- [ ] “新 session”模式可从工作树名称与提示词直接启动独立 worktree 会话
- [ ] “从消息 fork”模式可基于所选消息启动独立 worktree 会话
- [ ] 未输入自定义目录名时，目录创建位置与默认命名规则正确
- [ ] 输入自定义目录名时，目录创建位置正确且命名覆盖默认值
- [ ] 新 session 的 cwd 明确位于新 worktree
- [ ] 边界条件和异常场景处理正确

### 非功能测试
- [ ] 失败提示可明确定位失败步骤与恢复方式
- [ ] 不破坏现有 `/btw`、`/worktree-create`、现有 fork 新窗口能力
- [ ] 兼容现有 tmux/终端打开策略
